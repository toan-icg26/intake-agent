# Discovery Brief — Intake-to-Resolution Agent

**Track:** C · Agent — Free-Tier Agent Lab
**Author:** Toan Nguyen
**Date:** 15 September 2026

---

## 1. The customer

**Lumen Industrial** (fictional) — a mid-size industrial components manufacturer, ~1,200 employees across three plants and one head office. No dedicated ITSM product team; IT runs lean.

**The team in scope:** the internal **IT Service Desk** — 12 agents on first line, plus four downstream resolver groups:

| Resolver group | Owns |
|---|---|
| Network & Infrastructure | connectivity, VPN, servers, plant network |
| Business Applications | ERP, MES, reporting, integrations |
| End-User Devices | laptops, printers, peripherals, OS |
| Identity & Access | accounts, permissions, MFA, joiners/leavers |

Anything touching a security incident or a stopped production line goes to a fifth path: **human escalation to the IT duty manager**.

## 2. The users

- **Requesters** — any of the 1,200 employees. Most are not technical. They describe symptoms, not causes ("SAP is broken", "I can't get in").
- **First-line agents** — the 12 people who currently read every incoming request and decide category, urgency and owner.
- **IT duty manager** — the person who must be told immediately when something is genuinely P1.

## 3. The workflow as it runs today

1. Requests arrive through **three uncoordinated channels**: a shared mailbox, a web form, and phone calls that agents transcribe by hand.
2. A first-line agent reads each one and manually assigns: a **category**, an **urgency**, and a **resolver group**.
3. If the request is incomplete — which is common — the agent emails back asking for missing details, and the ticket sits idle until the requester replies.
4. If the agent guesses the resolver group wrong, the receiving team bounces it back or sideways. The SLA clock does not reset when this happens; the ticket simply loses hours.
5. P1 incidents are supposed to be escalated immediately, but escalation depends on whether the agent on duty recognises the signal in the text.

## 4. The pain point

Manual triage is the bottleneck, and it fails in three specific ways:

- **Misrouting.** Industry benchmarks put first-attempt misrouting at up to 30% of tickets, with 15–25% of manually triaged tickets reassigned at least once. Each reassignment adds roughly 47 minutes to resolution time. A reassignment rate above 15% is generally treated as a structural problem rather than an agent problem.
- **Idle time on incomplete requests.** A request missing its asset tag, error message or affected user count cannot be worked. Today nobody notices until an agent picks it up, which may be hours after arrival.
- **Inconsistent escalation.** P1 recognition is a human judgement made under load. Internal service desks resolve only ~44% of incidents on first contact (vs ~60% for outsourced desks), so there is meaningful volume flowing through handoffs where a missed P1 can hide.

At Lumen's volume — roughly **800 requests per week** across the three channels — a 28% misroute rate is ~224 tickets a week going to the wrong place first.

**The one that matters most:** a *missed* escalation is far more costly than a misroute. A ticket sent to the wrong team loses hours; a stopped production line treated as routine loses a shift.

## 5. Systems involved

- Intake channels: shared mailbox, web form, phone notes (all represented as **synthetic text records** in this project — no real mail server is connected).
- The agent itself: **SAP CAP** service on **BTP trial**, developed in Business Application Studio.
- Model: **Groq free tier**, OpenAI-compatible endpoint (`https://api.groq.com/openai/v1`), model `openai/gpt-oss-120b` (the originally planned `llama-3.3-70b-versatile` was not available to this account on 15 Sep 2026).
- Persistence: CAP's built-in SQLite for local development.
- No downstream system is written to. The agent proposes; a human approves.

## 6. Constraints

| Constraint | Consequence for the design |
|---|---|
| **No SAP AI Core on a trial account** | No Joule, no Document Grounding, no generative AI hub. The model comes from an endpoint I control. This is the premise of the track, not a defect to work around. |
| **No paid tooling** | Groq free tier: no credit card; 1,000 requests/day and 8,000 tokens/minute for this account. Batch evaluation runs (50 fixtures) must be throttled or they will hit HTTP 429. |
| **No customer data, no client systems** | Every request in this project is synthetic and generated by me. The agent is never pointed at a system I do not own. |
| **Trial dev space limits** | BAS trial dev spaces are deleted after 30 days idle; the repo is the source of truth, not the dev space. |
| **Latency is user-visible** | First-line agents will not wait 30 seconds for a classification. Response time is recorded from assignment 1 onward. |

## 7. Success metric

**First-pass routing accuracy** — the percentage of requests assigned to the correct resolver group *without any subsequent reassignment*.

- **Measured how:** replayed against a committed fixture set of 50 synthetic requests, each with a human-labelled correct resolver group. Accuracy = correct assignments ÷ total assignments.
- **Baseline:** ~72% (derived from the benchmark misroute rate of up to 30% for manual triage).
- **Target:** ≥ 90% first-pass accuracy.
- **Hard gate that overrides the headline number:** **missed escalations must be zero.** A system at 95% routing accuracy is still unusable if the 5% it misses are all P1s. This is why assignment 11 inspects failures by category rather than reporting a single score.

## 8. What the agent decides

For each incoming request the agent produces structured fields — not prose — and selects exactly one of four paths:

1. **Ask for missing information** — required field absent, cannot be triaged yet.
2. **Draft a response** — a known, documented resolution exists.
3. **Route to a resolver group** — needs a specialist, no emergency signal.
4. **Escalate to a human** — P1 signal present, or the request is outside policy and must be refused by a person.

## 9. The policy boundary (what the model is not allowed to decide)

These checks run in **application code**, before and after the model, and can override it:

- **P1 signals** — production line stopped, safety system affected, suspected security breach, data loss, or more than 50 users impacted. If a P1 signal is matched, the request escalates regardless of what the model concluded.
- **Refusal cases** — requests asking for another person's credentials, or for access changes without an approver named, are refused. The model does not get a vote.
- **Completeness rules** — a request without an identifiable requester or affected system cannot be routed, only returned for information.

The model classifies and explains. Code decides anything expensive to undo.

## 10. Out of scope for this project

- Writing back to any ticketing system.
- Real email or telephony integration.
- Multi-language intake (English only).
- Fine-tuning. The model is used as served.
